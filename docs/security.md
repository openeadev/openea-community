# Security Policy

OpenEA Community 1.0 includes Argon2id password hashing, signed HttpOnly browser sessions, SameSite cookies, CSRF protection for browser writes, temporary authentication lockout/backoff, server-side role authorization, validated dynamic schemas, SQLAlchemy parameterized database access, immutable PostgreSQL audit events, baseline security headers, and configuration-based secrets.

The REST API uses the same authenticated server-side session and authorization rules in the MVP. API write access does not bypass object-property, relationship, governance, or role validation.

For production deployments, use a long random `SECRET_KEY`, expose OpenEA only through HTTPS, set `BASE_URL` to the HTTPS public URL so cookies receive the Secure flag, protect PostgreSQL from untrusted networks, and keep `DEBUG` disabled. Back up PostgreSQL before upgrades and bulk imports.

Do not publish exploitable security vulnerabilities in a public issue. Use the repository host's private security-reporting mechanism when available.

## API tokens and service accounts (1.3.0)

API token secrets are generated by OpenEA Community and displayed only once. OpenEA stores a SHA-256 digest, token prefix, scopes, expiration, revocation state, and last-used timestamp; plaintext secrets are not recoverable from the database. Revoke a suspected token immediately from `/account/tokens` or, for Platform Administrators, `/admin/api-tokens`.

Service accounts are non-interactive identities and are explicitly rejected by the password login flow. Their API authority is the intersection of assigned OpenEA application roles and each token's scopes.
